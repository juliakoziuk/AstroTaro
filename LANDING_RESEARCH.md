# Лендінг MYSTIQ: як відтворити референс максимально точно

Дослідження інструментів + результати вимірювань на вашому референсі (`img.png`, 1024×683).

## 0. Коротко

1. **Референс — растр.** Це AI-картина з вшитим текстом, а не векторний макет. «Піксель у піксель» точно відтворюють лише піксельні дані; вектор — це завжди наближення.
2. **Найточніший робочий підхід — гібрид**, і саме його зібрано:
   - **плита** — пікселі референсу *без* тексту й іконок (скрипт стирає їх і добудовує фон);
   - **іконки, логотип, стрілка** — справжній вектор (трасування «оригінал − плита» на кількох порогах яскравості);
   - **текст і кнопки** — живий HTML; шрифт, кегль, трекінг, позиція й колір **підібрані автоматично** за піксельною різницею з референсом;
   - **стенд порівняння** (puppeteer + pixelmatch + SSIM) — числа замість «на око».
3. **Повністю векторна сцена теж зроблена** (`?art=vector`), але вона важить мегабайти й гірша за точністю — див. таблицю нижче.

## 1. Чому «усе вектором» не дає точності

- **Градієнти SVG — лише лінійні й радіальні.** «Сітчасті» (mesh) градієнти, потрібні для живописних переходів, залишились поза SVG 2 (перенесені до 2.1) і не мали реалізацій у браузерах (за джерелами 2016–2018; актуальність перевірте на MDN/caniuse). Живописне світло й зерно в SVG — це лише тисячі накладених контурів.
- **Автотрасування (vtracer, Illustrator, Vectorizer.AI)** квантує кольори в плоскі шари → «постеризація», а повна сцена виходить у мегабайти: див. вимірювання.
- **Дослідницькі методи (DiffVG, LIVE)** оптимізують контури під картинку, але повільні (десятки секунд на шар), потребують CUDA/старих компіляторів і погано масштабуються на сцену з тисячами дрібних деталей.

## 2. Карта інструментів

| Завдання | Інструмент | Висновок |
|---|---|---|
| Растр → кольоровий SVG | **vtracer** (open-source, Rust) ✅ використано; Vectorizer.AI (платний; в оглядах вважається найкращим автоматичним, але огляди слабкі); Illustrator *Image Trace* (багато керування, відгуки суперечливі); Inkscape *Trace Bitmap* | Для сцени дає наближення, не копію |
| Лінійна графіка (іконки, логотип) | **multi-level potrace** ✅ власна реалізація на vtracer: різниця «оригінал − плита» → 3 пороги → прозорі шари одного кольору | Дуже близько до оригіналу, десятки КБ |
| Прибрати текст з картинки | **власний гармонічний inpaint + перенесення зерна** ✅; LaMa (ONNX, потрібна маска; ~1.6 с на CPU; перевірте ліцензію даних) — резерв; Gemini / Photoshop Generative Fill — якщо треба «домалювати» велику область | Для тонкого тексту на гладкому фоні власного методу достатньо |
| Збільшити роздільність | **Real-ESRGAN** (ncnn-vulkan, `realesrgan-x4plus`) ✅ використано: ціла плита ×4 за 19 с на RTX 3050; GUI **Upscayl** — та сама модель; Topaz Gigapixel (платний) | Не беремо «як є», а лише «деталь» від ШІ — див. розділ 4a |
| Нова чиста ілюстрація | **Gemini (Nano Banana Pro)** — за сторонніми джерелами 1K/2K/4K; просити «ту саму сцену, 16:9, без тексту й інтерфейсу» | Дає вищу роздільність, але композиція трохи відрізнятиметься від референсу |
| Вимірювання відповідності | **pixelmatch**, власний SSIM, **puppeteer-core + Chrome** ✅; Playwright `toHaveScreenshot` — те саме для CI | Дозволяє автоматично підбирати параметри |
| Підбір шрифту | **власний координатний спуск за MAE** ✅ (перебір сімей × кегль × трекінг × інтерліньяж × позиція) | Знайшов, що заголовок — Gelasio, а не Playfair |
| Формат плити | **WebP** ✅ + `srcset` 1x/2x(/4x); AVIF — до ~20–50 % менше при тій самій якості (дані різних блогів розходяться) | |

## 3. Конвеєр (що де лежить)

| Крок | Команда / файл |
|---|---|
| Чиста плита + `srcset`-варіанти, потім вектор (сцена, іконки, логотип, стрілка) | `npm run landing:plate` → `src/landing/art/plate-*.webp`, `src/landing/art/traced/*` |
| Піксельне порівняння з референсом | `npm run landing:diff` (`ART=vector` — вектор-режим), потрібен запущений `npm run dev` |
| Знімки на типових екранах ПК | `npm run landing:shots` (або `node scripts/landing-shots.mjs 1920x950 3440x1300`) → `node_modules/.cache/landing-shots` |
| Автопідбір шрифтів, кольорів, кнопок, ваги | `npm run landing:fit` (окремо: `scripts/fit-text.mjs`, `fit-boxes.mjs`, `fit-polish.mjs`) |
| Вимір геометрії референсу | `node scripts/measure-reference.mjs` |

Як це влаштовано: сцена має розмір 981×639 («піксельна сітка» референсу). У CSS одиниця `--u` = 1/981 ширини сцени, тож будь-яку позицію пишемо числом з референсу: `calc(var(--u) * 148.5)`. Сцена масштабується цілком і лишається 1:1 на екрані ≈981 px.

## 4. Результати

Вимірювання: рендер сторінки рівно 981×639 у Chrome, порівняння з вирізаною сценою `img.png` (SSIM — структурна схожість, 1.0 = ідентично; MAE — середня помилка по каналах 0–255).

| Версія | SSIM | MAE | Арт |
|---|---|---|---|
| Було: трасована сцена + текст «на око» | 0.793 | 10.3 | SVG 4.4 МБ |
| `?art=vector`: трасування + підібраний текст | 0.897 | 6.3 | SVG 4.4 МБ (1.2 МБ gzip) |
| **За замовчуванням: плита + вектор-іконки + підібраний текст** | **0.950** | **4.3** | WebP 136 КБ (1x) і 142 КБ (2x) |

По зонах (за замовчуванням): шапка 0.958 · hero-текст 0.822 · кнопки 0.940 · арт-сцена **0.996** · панель 0.972.

**Скільки коштує вектор.** Трасування арт-зони (SSIM лише по зоні арту, референс — 1.0 для плити в 1x):

| Налаштування vtracer | Розмір SVG (gzip) | Контурів | SSIM арту |
|---|---|---|---|
| стандартне (у проєкті) | 4.3 МБ (1.2) | 14 тис. | 0.880 |
| дрібніше | 7.4 МБ (2.0) | 26 тис. | 0.907 |
| максимальне | 13.8 МБ (3.9) | 45 тис. | 0.935 |
| плита WebP 1x | 0.14 МБ | — | 0.996 |

Тобто навіть 14 МБ вектора не дотягують до 140 КБ растру.

**Що підібрав автопідбір (за піксельною різницею, не на око):**
- заголовок — **Gelasio 400**, 38 px (не Playfair, як я вгадував раніше); «MYSTIQ» — Lora 400;
- абзац і «LOSTIQ» — **Heebo** (Roboto-подібний), ≈16 px, інтерліньяж 21.75 px, вага ≈450;
- підписи панелі й кнопки — **Roboto Condensed** (600 і 400), 28.4 і 18.4 px;
- геометрія кнопок і кнопки мови — з виміряних пікселів референсу, включно з чорними «кільцями» навколо рамок (артефакт передискретизації референсу, який теж відтворено).

**Чому не 1.000.** Залишок — майже весь у **літерах**: текст у референсі намальований ШІ (у ньому навіть «Васної долі» й деформована «я»), тому жоден справжній шрифт не збігається з ним по формах. Підсвічування, затінення, зерно, візерунки й тіні в арті — це пікселі оригіналу й збігаються на 0.996.

**Нюанси чесно:** 1) справжньої інформації в плиті стільки, скільки в референсі (1024 px); на широких екранах береться 4×-версія з додатковою ШІ-деталлю — вона чіткіша на вигляд, але нових реальних деталей не з'являється (їх дасть лише нова генерація, див. нижче); 2) нижня панель у плиті намальована, на мобільному розкладка інша (плита обрізається до арту); 3) огляди векторизаторів у джерелах — маркетингові, тому порівнюйте на своєму зображенні.

## 4a. Як піднести якість далі

1. ✅ **ШІ-апскейл плити ×4 — зроблено** (Real-ESRGAN `realesrgan-x4plus`, офіційний реліз v0.2.5.0). `plate-4x.webp` (3924 px, 354 КБ) лежить у `srcset`: браузер бере його, коли потрібно більше 1962 px (широкий екран або Retina), на звичайному екрані без змін береться 1x.

   **Чому не просто вставити результат ШІ.** Я порівняв моделі на фрагменті арту, зменшивши результат назад до розміру оригіналу (чесний ШІ-апскейл після зменшення має збігатися з вихідною картинкою):

   | Варіант | SSIM після зменшення назад | Різкість | Коментар |
   |---|---|---|---|
   | Звичайний Lanczos ×4 | 0.982 | 7.2 | вірний, але м'який |
   | `x4plus` повністю | 0.952 | 13.6 | різкий, але зсуває тони й вигадує плями |
   | `x4plus-anime` | 0.942 | 12.6 | мультяшний вигляд — відпав |
   | `animevideov3` | 0.978 | 8.6 | майже як Lanczos |
   | **Lanczos + «деталь» від `x4plus` (σ 3, k 0.65)** | **0.983** | **12.1** | тони оригіналу + різкість майже як у ШІ |

   Тобто від ШІ береться лише високочастотний шар (оригінал мінус розмиття), що додається до чесного Lanczos. Відтворити: `realesrgan-ncnn-vulkan -i src/landing/art/plate-clean.png -o plate-x4plus.png -n realesrgan-x4plus -s 4 -g 1`, потім `HI_RES=plate-x4plus.png npm run landing:plate` (`-g 1` = відеокарта NVIDIA; `AI_DETAIL_K` керує силою деталі).
2. **Нова чиста ілюстрація від Gemini** у 2K/4K. Просіть саме арт: «Та сама сцена: арка з півмісяцем праворуч, свічки на сходах, темна ліва частина для тексту; 16:9; без тексту, кнопок, панелей і інтерфейсу; максимальна роздільність». Композиція буде трохи іншою, ніж у референсі, тому плиту треба буде перекласти й перепідібрати координати.
3. **Решта екранів** (Login, Pricing тощо): та сама схема — плита без тексту + живий HTML. Форми й таблиці краще верстати HTML, векторизувати лише декоративне.

## 4b. Адаптація під екран комп'ютера

**Було:** сцена — картка фіксованої пропорції 981:639 по центру. На звичайному моніторі (≈16:9) по боках лишались порожні смуги (на 1920×950 по 231 px), було видно рамку референсу, а на ультрашироких екранах — маленька картка в порожньому полі.

**Стало:** повноекранна сторінка без смуг і без рамки-картки. Правила:
- Масштаб `--u` береться з висоти вікна (або з ширини, якщо вікно вужче за референсну пропорцію), тож усе вміщається без прокрутки.
- Шапка, текст і кнопки тримаються лівого краю, кнопка мови — правого, «MYSTIQ» — центру; арт — правого краю. Панель займає всю ширину, чотири колонки рівні, роздільники між ними малює CSS.
- Плита розрізана на ліву (x < 335) й праву (x ≥ 335) частини. На ширших за референс екранах вони розсуваються, а проміжок заповнює плитка `fill.webp` (медіана рядків біля розрізу + синтетичне зерно, без візерунків, що могли б повторюватись). Краї частин плавно «розчиняються» в плитці на ширину до 60 одиниць, а на референсній пропорції проміжку немає — пікселі ті самі.
- Рамку-«картку» референсу прибрано (краї затікають сусідніми пікселями на 4 px).
- Вікна вищі за референс (до 1:1, наприклад 5:4): композиція по центру, верх і низ плавно сходять на фон. Вужчі за 720 px або портретні вікна — колонкова розкладка (на ній арт — верхні 439 з 639 px плити).

**Перевірено** у Chrome: 1366×650, 1536×730, 1920×950, 2560×1300, 3440×1300, 1280×1024, 1024×700, 800×900, 375×812 — без прокрутки й без помилок у консолі (`npm run landing:shots`). На референсній пропорції SSIM 0.946 (зона без крайових 6 px, де в референсі була рамка); панель 0.971, арт 0.996. Production-збірка (`vite build`) проходить.

**Обмеження:** не перевіряв у Firefox (використано `round()`, `clamp()`, `mask-image`, `svh` — усе є в Firefox ≥ 118); на надшироких екранах проміжок між текстом і аркою синтетичний (темне поле зі зерном), а «двері»-силует рухається разом із аркою праворуч.

## 4c. Екран Login (`/login.html`)

Той самий метод, що й для лендінгу, на референсі `reference/login.webp` (1535×1024):
1. **Відтінок синього = Landing.** `scripts/lib/grade.mjs` порівнює медіанні насиченість і відтінок «синіх» пікселів за смугами яскравості в плиті лендінгу й у Login та перебарвлює Login (золото й нейтральні кольори не чіпає). Після підгонки смуги збігаються з лендінгом: відтінок 210°, насиченість 0.83 / 0.80 / 0.60 проти 0.83 / 0.81 / 0.58.
2. **Що лишається пікселями, що стає живим.** Лишаються: арт, рамки полів, «шкіра» кнопок, активна пілюля «Home», трек перемикача, місяці й зірки з сяйвом (градієнтне світіння векторні шари передають пласким). Стираються лише штрихи тексту й значків (поріг + заповнення замкнених дірок + гармонічний inpaint на піраміді, `scripts/lib/inpaint.mjs`). Живі: текст, векторні значки, логотип Google (SVG), поля вводу, чекбокс, «око».
3. **Вектор** — `scripts/lib/ink.mjs` (multi-level potrace, кольори шарів регуляризовані на малих значках).
4. **Широкі екрани** — плита розрізана посередині картки; половини розсуваються й м'яко розчиняються перед «діркою» під картку (`--hole`, `--fade` у `login.css`), проміжок заповнює плитка зі зерном; сайдбар тримається лівого краю.
5. **Інтерактивність:** показ/приховування пароля, чекбокс, фокус-glow полів, наведення/натискання кнопок, фокус з клавіатури, Enter не перезавантажує сторінку.

**Метрики** (рендер 1535×1024 проти перебарвленого референсу): SSIM загалом **0.983**, арт 0.995–0.996, сайдбар 0.980, поля 0.971, кнопки 0.968, верх картки 0.963. Залишок — переважно форми літер.

Команди: `npm run login:build` (матеріали з референсу), `npm run login:diff` (метрики, потрібен `npm run dev`), `npm run login:fonts` (ранжування шрифтів за пропорціями рядків), `npm run login:fit` (підбір шрифтів і кольорів).

**Шрифти інтерфейсу (як вибирались).** Підбір лише за піксельною різницею тут оманливий: текст у референсі намальований ШІ, тож різниця «тяжіє» до тонких, тьмяних накреслень, а на «Sign In» чи «Continue with Google» дає найгірші результати саме для шрифтів, що ближчі за формою. Тому вибір зроблено в три кроки:
1. `npm run login:fonts` (`rank-fonts.mjs`) — ранжування 60+ шрифтів за пропорціями рядків (відношення ширини чорнильної рамки до висоти для 14 рядків). Noto Sans відхиляється на ≈10 %, найближчі — Alegreya Sans і Encode Sans (≈2 %), Jost, Cabin.
2. `fit.mjs` — для кандидатів підібрано кегль, трекінг, позицію, вагу (різниця при розмиттях σ 2.5 → 1 → 0).
3. `fit-mass.mjs` — вага й трекінг вирівнюються за «масою чорнила» (сума яскравості штрихів над фоном; від форм літер майже не залежить): маса тексту в мене тепер 0.98–1.02 від референсу в кожному блоці.
4. Для кожного блоку порівняно реальну схожість на сторінці (SSIM у зоні) для Noto Sans і Encode Sans і лишено кращий: **Encode Sans** — плейсхолдери (0.894 проти 0.870), «Remember me» (0.916 проти 0.840), «Sign In» (0.814 проти 0.737), «Continue with Google» (0.776 проти 0.571), «or» (0.954 проти 0.863); **Noto Sans** — меню (0.931 проти 0.919), підзаголовок (0.890 проти 0.847), футер (0.868 проти 0.674), «Forgot password?» — майже порівну.

Підсумок після цього: SSIM загалом **0.983**, поля **0.971**, кнопки **0.968**, футер 0.961. Решта розбіжності в тексті — це форми літер ШІ-малюнка, жоден справжній шрифт їх не збігає.

**Не доведено / відомі розбіжності:**
- Повзунок перемикача теми в референсі — двотонний (світла ліва й сіра права половина з різким переходом); горизонтальний градієнт CSS дає майже ту ж схожість (0.85), різкий перехід її не покращує, тому лишено м'який.
- Firefox не перевіряв; мобільну розкладку — лише в емуляції.

## 4d. Решта екранів застосунку (`/app.html`)

**Вхідні дані.** Папка `imgase/` (12 макетів 1536×1024). Login був готовий раніше; додано **11 екранів**: Register, Pricing, Dashboard, Tarot Studio, Tarot Reading, Dream Journal, Dream Analysis, Astrology, AI Companion, Profile, Settings. Вони зібрані в один застосунок `app.html` з hash-маршрутами: `#/dashboard`, `#/register`, `#/pricing`, `#/tarot`, `#/reading`, `#/dreams`, `#/analysis`, `#/astrology`, `#/companion`, `#/profile`, `#/settings`. Landing і Login — теж екрани цього ж застосунку (див. 4e).

**Конвеєр** (`scripts/app/`; 11 екранів по одному вручну робити неможливо, тому процес автоматизований):
1. `prepare.mjs` — перебарвлення синього макета під Landing (криві S/H за смугами яскравості + вирівнювання темної бази, `lib/align.mjs`). Темна база макетів була (4,16,27) проти (11,24,38) у Landing.
2. `detect.mjs` — автоматичне виявлення рядків тексту й дрібних елементів (відхилення від локального фону, злиття літер у рядки, тісний bbox за порогом від піку, колір чорнила). `npm run app:detect` складає розмітку `node_modules/.cache/app-build/<id>.det.png` з номерами рядків.
3. `specs/<id>.mjs` — опис екрана коротким форматом (`dsl.mjs`): «номер рядка, клас тексту, сам текст» плюс `@sidebar`, `@hit` (клікабельні зони), `@toggle`, `@radio`, `@check`, `@select`, `@input`. Текст набирається вручну за макетом, позиції — з виявлення.
4. `build.mjs` — виміри в Chrome (canvas.measureText): кегль, трекінг і позиція кожного рядка підраховуються аналітично, без перебору; кегль спільний для класу тексту. **Вага — за масою чорнила** (площа покриття літер у canvas проти маси чорнила в макеті), у межах ±200 від типової ваги класу й не тонше за 400. Далі текст і замінювані контроли стираються з макета (гармонічний inpaint на піраміді + перенесення зерна), результат — плита `src/app/art/<id>.webp`, дані — `src/app/data/<id>.json`.
5. `src/app/Screen.jsx` рендерить дані: живий текст, клікабельні зони, перемикачі, радіо, галочки, `<select>`, поля вводу.

**Шрифти.** Ранжування ~140 гарнітур за пропорціями рядків (`npm run app:fonts`), потім порівняння 9 пар за реальною схожістю на сторінці (`scripts/app/try-fonts.mjs`): серіф **Crimson Text**, без засічок **Source Sans 3**.

Найнижчі екрани (Dream Journal/Analysis, Companion) — найтекстові: багато дрібного тексту поверх мініатюр і світіння.

**Інтерактивність** (`npm run app:test`; повний перелік і карта переходів — у 4e): усі маршрути, меню сайдбара, картки дашборда, радіо й вибір колоди в Tarot Studio, перемикачі в Settings, поля й галочка в Register, поле чату, посилання Landing → застосунок → Login. Контроли справжні (`role=switch/radio/checkbox`, `<select>`, фокус з клавіатури).

**Широкі екрани.** Сайдбар тримається лівого краю вікна, решта екрана центрується в залишку ширини, краї центральної частини плавно розчиняються в розмитій копії плити (`.ambient`); на пропорції макета 3:2 шва немає. Вікна вищі за макет — верх і низ плавно сходять на фон. Портретні вікна — макет за висотою з гортанням убік.

**Обмеження:**
- Тексти екранів — англійською, як у макетах; дані демонстраційні (бекенду немає).
- На надшироких екранах (≥ 21:9) між сайдбаром і контентом лишається широкий розмитий проміжок.
- Плити мають роздільність макета (1536 px); для Retina/4K чіткості не вистачає (потрібен ШІ-апскейл, як для Landing).
- Мобільної розкладки екрани не мають: на вузьких вікнах макет гортається вбік.
- Firefox не перевіряв.

## 4e. Один React-застосунок: усі 13 екранів і переходи між ними

Раніше лендінг, логін і застосунок були трьома окремими сторінками (посилання між ними перезавантажували сторінку). Тепер це **один React-застосунок** (`app.html`) з клієнтським роутингом: Landing, Login і 11 екранів за макетами; переходи без перезавантаження, працюють кнопки «назад/вперед» браузера.

**Як влаштовано**
- `src/app/router.js` — маленький роутер на hash-адресах (`#/dashboard`): `useRoute`, `go`, `back`, `navProps`. Hash-адреси не вимагають налаштувань сервера (працює на будь-якому статичному хостингу). `back('/запасний')` повертається по історії застосунку, а якщо екран відкрили прямим посиланням — веде на запасний екран. Посилання лишаються справжніми `<a href>` (відкриваються в новій вкладці з Ctrl/⌘-кліком).
- `src/app/screens.js` — реєстр 13 екранів у порядку потоку; `src/app/App.jsx` — вибір екрана за маршрутом, заголовок вкладки, фон, плавна поява екрана (`.route`, відключається за `prefers-reduced-motion`).
- Стилі лендінгу, логіну й застосунку мали однакові імена класів (`.page`, `.stage`, `.t`…), тому їх огорнуто префіксами `.v-landing`, `.v-login`, `.v-app` скриптом `scripts/scope-css.mjs` (PostCSS); глобальна база — `src/app/base.css`. Візуальної різниці немає: SSIM лендінгу 0.948, логіну 0.983, екранів застосунку — як раніше.
- Старі адреси `landing.html` і `login.html` лишилися й перенаправляють у застосунок (разом із `?query`, напр. `?art=vector`).
- **Перемикач екранів** для демо: дрібна кнопка в правому нижньому куті відкриває список усіх 13 екранів. Клавіші: **G** — відкрити/закрити, **Esc** — закрити, **[** і **]** — попередній/наступний екран. З `?clean` в адресі перемикач ховається (так знімаються еталонні знімки для порівняння з макетами).

**Карта переходів** (крім бічного меню, спільного для екранів із макетів: логотип → Dashboard, Home → Dashboard, Chat → AI Companion, Analytics → Dream Analysis, Access → Pricing, Settings → Settings, Help → Settings):

| Екран | Що клікається → куди |
|---|---|
| Landing | «Розпочати» → Register; «Вхід» → Login; картки Таро → Tarot Studio, Діаріум снів → Dream Journal, Астрологія → Astrology, ШІ Асистент → AI Companion; логотип → Landing |
| Login | Sign In і Continue with Google → Dashboard; Sign Up → Register; меню зліва (як у застосунку); «око» показує пароль; Forgot password? — без переходу (екрана в макетах немає) |
| Register | Create Account → Dashboard; Sign In → Login; «око» в обох полях пароля показує/ховає введене |
| Pricing | Get Started → Register; Upgrade і Choose → Dashboard |
| Dashboard | Tarot → Tarot Studio; Dreams і Journal → Dream Journal; Astrology і Monthly Insight → Astrology; AI Companion → AI Companion; Progress, Your Activity, Your Progress → Profile |
| Tarot Studio | будь-який розклад і Start Reading → Tarot Reading; радіо й вибір колоди — живі |
| Tarot Reading | Back → назад (запасний Tarot Studio); Save Reading → Profile; New Spread → Tarot Studio |
| Dream Journal | Back → назад (запасний Dashboard); будь-який сон → Dream Analysis |
| Dream Analysis | Back → назад (запасний Dream Journal); Add Dream → Dream Journal |
| Astrology | Generate Report → Pricing |
| AI Companion | Back → назад (запасний Dashboard); Tarot Advisor → Tarot Studio; Astrologer → Astrology; Dream Interpreter → Dream Analysis; кнопка надсилання очищає поле (Enter теж) |
| Profile | Back → назад (запасний Dashboard); Edit Profile, Email, Password → Settings; плитки Readings → Tarot Reading, Dreams → Dream Journal, Reports → Astrology; Saved Readings → Tarot Reading; My Reports → Astrology; Log Out → Login; перемикач і списки — живі |
| Settings | Back → назад (запасний Profile); перемикачі й списки — живі |

Частина призначень — **моє припущення**, бо в макетах немає екранів-адресатів (Save Reading → Profile, Generate Report → Pricing, Upgrade/Choose → Dashboard, Monthly Insight → Astrology, Help → Settings). Усе змінюється в одному місці: рядки `@hit … #/маршрут` у `scripts/app/specs/<екран>.mjs`, далі `npm run app:build -- --no-plate` (плити не перебудовуються, ~20 с). Елементи, яким нема куди вести (Share, Favorites, History, розділи меню Settings, картки Astrology, «Edit/Delete» у снах), лишаються без переходу й без підсвічування наведення.

**Перевірка** (`npm run app:test`, 187 перевірок у Chrome; ті самі проходять на production-збірці): усі 13 екранів відкриваються; **кожне посилання з даних екранів** (усі зони й текстові посилання) веде на свій екран клієнтським переходом (маркер у `window` не зникає, тобто сторінка не перезавантажується); «назад» з історією й без неї; кнопки «назад/вперед» браузера; сайдбар; кліки по Landing і Login; перемикач екранів і клавіші; радіо, перемикачі, select, «око», галочка, поле чату; старі адреси; невідомий шлях веде на лендінг; помилок у консолі немає.

**Обмеження:** немає екрана «забули пароль» і форм для нового сну; логін і реєстрація демонстраційні (без бекенду, будь-який вхід відкриває Dashboard); перемикач теми (сонце/місяць) у сайдбарі намальований у плиті й не клікається; бічне меню завжди підсвічує Home (як у макетах), тож активний пункт не змінюється при переході.
